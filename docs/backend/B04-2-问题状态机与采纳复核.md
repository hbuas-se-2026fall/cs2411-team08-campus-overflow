## 背景与目标

B04-1 把 S2 的 30 处 TODO 清零后，本批叠加任务清单 T2 的治理类新需求。前端 F05/F07 依赖撤销采纳与教师复核端点，因此本批一并落地。用户确认按建议执行：**加 close 端点、DELETE 请求体传撤销原因、撤销采纳权限 = 提问者 + 课程管理者**。

内容：

1. 问题状态机（`OPEN/RESOLVED/CLOSED/DELETED`）与关闭治理；
2. 撤销采纳 `DELETE /questions/{id}/accepted-answer`；
3. 教师复核 `POST /questions/{id}/acceptance-reviews`（理由 + `expectedVersion` 乐观锁）；
4. 认证历史留痕 + 撤销认证（编辑自动使认证失效）；
5. 回答来源标记 `HUMAN/AI/AI_ASSISTED`；
6. 详情回答分页。

**按 YAGNI 暂缓**：`MERGED` 状态（前端未依赖、需跳转语义）、AI 回答提交入口（属 S3）、AI 反馈通道、悬赏（属 S3）。本批 `source` 只落字段与展示，提交时服务端固定 `HUMAN`。

## 设计决策

### 兼容性手法（后续批次沿用）

- `Question.reconstitute` / `Answer.reconstitute` / `AnswerRow` / `QuestionRow` / `QuestionQueryService.detail` **全部保留旧签名重载**，新字段由旧签名推导默认值。这样既有测试（3 处直接调用 `reconstitute`）编译与断言**零改动**，只改了测试夹具实现与 `AnswerAndVoteServiceTest` 构造参数一行。
- **与方案的偏差 1**：方案写「`PermissionsView` 加 `canReview`/`canEndorse`」，实际改为放到 `QuestionDetailView` 顶层字段——`PermissionsView` 是 record，加 component 会破坏既有 `isEqualTo(new PermissionsView(4参))` 断言。
- **与方案的偏差 2**：复核表列名用 `question_version`（存的是**问题**版本快照，乐观锁），方案初稿的 `answer_version` 名不副实；`qa_endorsement_log.answer_version` 才是答案版本。
- **与方案的偏差 3**：撤销采纳所需的事件 `AnswerUnacceptedEvent`、`AnswerEndorsementRevokedEvent` 为新增（方案核对阶段发现 api 缺撤销类事件），纯追加供 S3 冲正。

### 其它

- **CLOSED 不被采纳覆盖**：关闭是教师治理的终态，独立于 `OPEN↔RESOLVED` 的采纳状态转换；关闭后拒绝回答与采纳（`QA-1027`）。
- **认证生命周期**：编辑回答会自动使认证失效并写 `REVOKE(EDITED)` 留痕 + 发冲正事件；`endorse` 写 `GRANT`；同版本重复认证由领域拒绝（`QA-1023`）。
- **乐观锁**：复核携带 `expectedVersion`，与问题当前 `version` 不符返回 409 `QA-1030`，防止基于过期状态做治理决策。
- **OCP / 纯追加**：新状态、新来源、新事件、新表均以追加方式引入，不改既有行为；`MERGED` 等无当前需求的能力不实现（YAGNI）。
- **采纳答案分页不变式**：无论分页如何切，采纳答案由 SQL 固定在第一页首位，保证前端始终能看到最佳答案。
