## 2. 背景与目标

B05 只实现了「个人账户 + 课程管理者」的悬赏基础状态机，且没有课程预算、没有幂等键、没有「一问题一开放悬赏」的数据库约束、终态并发没有条件更新保护；B05-2 又把「已花费积分被撤销后的待追回」和「悬赏是否随撤销回退」明确延后到 B06。本批把这些一次性收口：

- 悬赏资金来源分账：学生给自己的开放问题开个人悬赏，教师用课程预算开悬赏，两条资金池互不混用；
- 补齐边界、幂等、并发终态、到期/删除退款与争议留痕；
- 课程预算可查询、可分配，每笔增减都有来源/操作者/原因；
- 撤销后积分缺口正式建表并提供复核入口；
- 对 B05-2 遗留的三个悬而未决问题给出明确结论并落地。

## 6. 错误码

| 码 | 含义 | HTTP |
| --- | --- | --- |
| `REP-2001` | 无权为该问题发起该来源的悬赏（沿用，消息略调整） | 403 |
| `REP-2002` / `REP-2003` / `REP-2004` | 积分不在 10–500 / 期限不在 1–14 天 / 问题已关闭或已采纳（沿用） | 422 |
| `REP-2005` / `REP-2006` | 发起人不能赢自己的悬赏 / 悬赏已结束（沿用） | 422 / 409 |
| `REP-2007` | 悬赏或预算调整命令处理中（幂等 `IN_PROGRESS`） | 409 |
| `REP-2008` | 该问题已有开放悬赏、命令键重复、或悬赏课程与问题所属课程不一致 | 409 |
| `REP-2009` | 不支持的悬赏资金来源 | 422 |
| `REP-4001` / `REP-4002` | 问题不存在 / 声誉账户不存在（沿用） | 404 / 422 |
| `REP-5001` / `REP-5003` / `REP-5004` | 课程预算可用/冻结积分不足 / 金额必须非零或为正 | 422 |
| `REP-5005` | 课程不存在，或问题未关联课程却使用课程预算 | 404 |
| `REP-5006` | 仅管理员可调整预算 / 复核待追回 | 403 |
| `REP-5007` | 待追回记录不存在或已处理 | 404 / 409 |
| `REP-5008` | 无权查看该课程预算 | 403 |

## 7. 设计决策（含与方案的偏差，如实记录）

1. **预算归属 co-reputation（D1）**：新建 `rep_course_budget`/`rep_budget_adjustment`，`courseId` 只是归属键；课程存在性与状态经 `IdentityApi.findCourse` 校验，未改 `co-identity`，跨上下文仍只经 `*.api`。
2. **零类型分支（D3）**：资金用 `BountyFunding` 策略 + `BountyFundingRegistry` 按 `source()` 分派；授权用 `BountySource` 枚举 + Lambda。新增来源只需加一个枚举常量和一个策略类，`BountyService` 不改。
3. **两道独立的并发闸（D4/D5）**：客户端 `commandId` 走 `CommandIdempotencyStore`（`co_command_result`，与冻结同事务）防「同一请求重放」；`uk_bounty_open_question` 防「不同 key 并发双开」；`tryAward/tryExpire` 的 `WHERE status='OPEN'` 条件更新防「并发重复结算/退款」。`@Version` 乐观锁与 `uk_budget_event` 唯一流水是额外保障。
4. **`open_slot` 用普通列而非 MySQL 生成列**：JPA 映射更简单，由 `ReputationPersistenceAdapter.save` 按 `status` 统一维护（DRY）；迁移里对历史 OPEN 数据做了回填。
5. **既有构造函数全部保留**：`BountyService`（8 参数）、`ReputationEventHandlers`（6 参数）、`Bounty.open`/`reconstitute`（原签名）、`BountyRequest`（两字段）都以重载/兼容构造保留，Spring 主构造标 `@Autowired`。这是既有测试断言 0 改动的前提。
6. **偏差 — 个人退款不写 `rep_ledger`**：方案 D6 原写「个人退款记 `BOUNTY_REFUND` 的 POINTS 流水」，实现发现 `ReputationB05RulesTest.reasonCurrencySeparatesReputationFromPoints` 把 `namesOf(POINTS)` 固定断言为只含 `ANSWER_ENDORSED`。为不改既有断言，改为：冻结→可用属于**同一账户内部划转**，不记账本；唯一性由 `tryExpire` 条件更新 + `BountyClosedEvent` + `BOUNTY_CLOSED` 审计保证；预算侧退款仍记 `rep_budget_adjustment`。
7. **偏差 — 待追回不自动冲销**：方案 D10 原写「余额回升时 `/users/me/points` 查询自动把 PENDING 置 RESOLVED」，实现避免 readOnly GET 写库，改为 `PointsRecoveryView.currentGap` 实时展示账户缺口，由管理员在复核端点据此决策；`PointsRecovery.resolveAutomatically` 领域能力保留备用。
8. **偏差 — 端点路径加 `/api/v1` 前缀**：任务清单写 `POST /admin/courses/{id}/budget-adjustments`，项目所有端点统一 `/api/v1`，且 `SecurityConfig` 已有 `/api/v1/admin/** hasRole("ADMIN")`，故实现为 `/api/v1/admin/courses/...`，复用既有安全规则而非新增匹配器。
9. **D8 悬赏是否随撤销采纳回退：明确否决**。悬赏结算是终态；`AnswerUnacceptedEvent` 时若已 AWARDED 且获奖者是原答案作者，只置 `disputed=true` + 审计 `BOUNTY_AWARD_DISPUTED`，不冲正、不退款、不强扣。正式复核队列属 B10。
10. **D9 `BOUNTY_AWARDED` 币种重估：维持 REPUTATION**。既有测试规格断言获奖者 +N 声誉；悬赏金额守恒约束的是发起人侧 `available + frozen`；资金来源（积分）与奖励形式（声誉）本就不必同币种，改币种会破坏既有断言与 FlowIT 语义。
11. **悬赏授权放宽但旧路径保真**：B06 的 `PERSONAL` 允许提问者本人，`COURSE_BUDGET` 要求课程管理者且问题必须关联课程；B05 旧 `open` 签名仍只允许课程管理者，行为不变。
12. **`CampusOverflowFlowIT` 补验已完成（2026-11-25 夜）**：本机 Docker Desktop 4.92 / Engine 29.8 可用后跑了 `mvn -B verify`。Testcontainers 1.20.6 底层的 docker-java 默认协商旧版 API，被 Docker 29+（最低 1.44）以 `Status 400` 拒绝 `/info`；需在用户主目录新建 `~/.docker-java.properties` 固定 `api.version=1.44`（**纯环境配置，未改任何项目代码**）。修复后 MySQL 8 + Redis 7 容器正常启动，**10 个 Flyway 迁移全部应用成功（含 `202611250001 rep b05 reversal` 与 `202611250002 rep b06 budget`）**，Spring 上下文完整启动（`Started CampusOverflowFlowIT in 4.343 seconds`），证明本批新增的迁移、JPA 实体、2 个适配器与 3 个 Controller 都能在真实容器中装配、无 bean 歧义或循环依赖。IT 断言层面另暴露 4 个**既有基线缺陷**（详见第 8、9 节），与 co-reputation 无关，故未按本批范围擅自修改。**边界**：FlowIT 在「提问」阶段即被 `updated_at` 缺陷阻断，因此本批的悬赏/预算/待追回**业务链路仍只有单测覆盖**，未获端到端验证；本次补验只证明「迁移可执行 + 装配可成立」。
