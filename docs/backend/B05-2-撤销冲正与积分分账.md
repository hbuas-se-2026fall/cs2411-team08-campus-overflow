## 2. 背景与目标

B05-1 把 S3 的 71 处 TODO 清零，`mvn -B test` 已 27/27 全绿，但任务清单 T3 里的 B05 后半段尚未落地：B04-2 新增的两个撤销事件（`AnswerUnacceptedEvent` / `AnswerEndorsementRevokedEvent`）在声誉侧没有订阅者，教师认证只发徽章不发积分，也没有面向本人的积分查询端点。

本批目标：

1. 接上「采纳/认证 → 撤销 → 相反流水冲正」的闭环，且**只追加、不删账**（ADR-004）；
2. 把声誉与积分分成两本账的语义，避免积分流水污染 FF-8 对账、排行榜与搜索投影；
3. 提供 `GET /api/v1/users/me/points` 与 `/points/ledger`；
4. 负声誉对外展示为 0，账本保留真实负值。

**关键代码事实（调研结论）**：两个撤销事件都**不携带原事件 ID**，只有 `eventId / answerId / answerAuthorId / ...`。因此 `reverses_event_id` 无法从事件字段直接取，必须由声誉侧反查原流水得到。

## 7. 设计决策

| # | 决策 | 结论与理由 |
| --- | --- | --- |
| D4（沿用） | 徽章随撤销撤回？ | **不撤回**。ADR-004 只追加账本，徽章是历史成就 |
| D6（沿用） | 已花费积分被撤销是否本批建「待追回」表？ | **否，延 B06**。本批做到：余额允许为负（不静默截断）、`PointsView.pendingRecovery` 暴露缺口、`freezePoints` 天然限制支出 |
| D7 | 冲正如何定位原流水 | 按 `(userId, reason, refType, refId)` 找 `delta>0` 且 `reverses_event_id IS NULL` 的最新一条。自问自答（delta=0 从未记账）查不到 → 不冲正，避免凭空扣分 |
| D8 | 冲正幂等 | 两道闸：① `uk_ledger_event` 挡同一撤销事件重放；② `existsReversalOf(原eventId)` 挡不同撤销事件冲正同一条原流水 |
| D9 | 分账粒度 | **单表 + currency 标记**，不新建 `rep_points_ledger`。KISS/YAGNI，避免第二套账本与对账；`sumByUser()`、`findReputationByUser()`、`findPointsByUser()` 分别按事由集合过滤 |
| D10 | `BOUNTY_AWARDED` 币种 | **保持 REPUTATION 不变**。改币种会改变既有结算行为与 FlowIT 语义，超出「剩下的部分」 |
| D11 | 展示下限作用范围 | 只作用于 `profile`。`ReputationApi.summary/reputations` 是跨上下文发布语言，保留真实值供对账使用 |
| D12 | 负 delta 是否发 `ReputationChangedEvent` | **发**（仅 REPUTATION 币种），让榜单/搜索投影同步下降；POINTS 币种不发任何集成事件 |

### 与方案的偏差（如实记录）

1. **方案写「认证 +5 积分走独立的 points 记账路径」**，实现为**同一张 `rep_ledger` + `Currency` 标记**（D9）。原因是新建第二张账本会引入第二套对账与幂等逻辑，而 `sumByUser()` 过滤即可保证 FF-8 不失效。
2. **方案写「`ReputationReason` 扩 `ANSWER_ENDORSED` 等常量」**，实际只加 1 个常量——当前只有教师认证产生积分，其余事由没有需求（YAGNI）。
3. **方案写「`reverses_event_id` 记录冲正关联」**，实现发现撤销事件不带原事件 ID，改由 `findReversible` 反查原流水并把**原流水的 eventId** 写入该列；冲正流水自己的 `eventId` 用撤销事件的 ID。
4. **额外增强（方案未明说）**：`/reputation/ledger` 改为只返回 REPUTATION 币种流水，否则分账后声誉流水会混入 +5 积分条目，语义失真。
5. **实现中发现的既有隐患并修正**：`countByUserAndReason` 原为「按事由计数」，冲正流水 reason 沿用原事由，会让采纳计数虚增（撤销后重新采纳可能提前触发 `HELPER_10`）。现改为只统计「正向且非冲正」的流水，JPA 与内存夹具同步调整；既有测试断言未受影响。
6. **展示下限的位置**：方案说「展示层」，实现放在领域层 `ReputationAccount.displayReputation()`，让规则只有一处定义（DRY），`profile` 直接调用。
7. **AI 不发奖励**：按方案暂缓到 B09（需在 `AnswerSubmittedEvent` 加 `source` 后拦截）。
