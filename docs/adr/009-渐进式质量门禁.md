# ADR-009：渐进式质量门禁

**状态**：已接受 ｜ **驱动特征**：可演进性（交付节奏）、可验证性 ｜ **相关门禁**：FF-1~FF-6、领域覆盖率、端到端集成测试

## 背景
起始代码中 Q&A、Reputation、Discovery 三个上下文的核心方法尚未实现（`docs/学生任务清单.md` 的 107 个 `TODO` 方法），
随之失败的测试是实现完成的“验收单”，不是缺陷。若 CI 一上来就跑全量 `mvn test` 与集成测试：

- `develop` 会连续数个 Sprint 常红，而分支保护要求“必须通过状态检查”，等于**阻止一切合并**；
- 团队为了能合并，只能关闭状态检查或让失败测试“静默”，后者直接触碰学术诚信红线；
- 私有仓库共享组织每月 3,000 分钟 Actions 额度，单次全量运行（含 Testcontainers 与镜像构建）可超 10 分钟，
  多个小组并行开发很容易用尽，用完流水线会停跑，而 Sprint 验收恰恰依赖 CI 状态。

因此需要一种机制：**门禁的严格程度随实现进度上升**，而不是第一天就把未来两个 Sprint 的失败算在账上。

## 决策
1. **门禁范围由 `ci.yml` 的 `env.SPRINT_MODULES` 决定**：单元测试与覆盖率只跑“本 Sprint 计划必须为绿”的模块，
   由质量负责人在每个 Sprint 计划会后更新，随 PR 评审合入；S3 删除该变量，恢复全量。

   | 阶段 | `SPRINT_MODULES` | 覆盖率阈值 | 集成测试 |
   | --- | --- | --- | --- |
   | S0（当前：B01–B03 已完成，范围内全绿） | `co-shared-kernel` + Identity 五个子模块 | `co-identity-domain` 设 0.70（实测行覆盖 86%） | 允许失败 |
   | S1（B04 起） | 追加 `co-qa-domain`、`co-qa-application` | `co-qa-domain` 设 0.70 | 允许失败 |
   | S2（B05–B07） | 追加 `co-reputation-domain`、`co-reputation-application` | 再设 `co-reputation-domain` 0.70 | 允许失败 |
   | S3（B08–B12 及收口） | 删除变量，全量 | 根 POM 改为 0.70 | 硬门禁 |

   阶段编号沿用指导书 8.3 的 S0–S4；本组按《后端详细开发计划》的 B 批次推进，表中的括号只是“该阶段范围对应哪些 B 项”，
   每次 Sprint 计划会仍以当场确认的模块清单为准（更新 `SPRINT_MODULES` 并走 PR）。

2. **范围必须列到具体子模块**：Maven 的 `-pl` 不会展开父聚合模块（`-pl co-identity` 只构建 `pom` 本身），
   写成聚合模块会得到“构建成功但一个测试都没跑”的假绿。
3. **`co-bootstrap` 不进 `SPRINT_MODULES`**：它依赖全部上下文，`-am` 会把尚未实现的上文法拉进反应堆并执行其失败测试。
   B01 的平台基础单测（`RequestIdFilterTest`、`InternalAuthFilterTest`）与 ArchUnit 合并为一步：
   `-pl co-bootstrap -am -Dtest='ArchitectureTest,RequestIdFilterTest,InternalAuthFilterTest'`，
   复用同一次全模块编译，不额外增加构建成本。
4. **不变的硬门禁**：全量编译（`clean compile`）、ArchUnit（FF-1~FF-6）、前端 `typecheck` + `build`。
   它们在任何阶段都必须绿——这三个是“工程结构没坏”的底线，与业务实现进度无关。
5. **集成测试 S0–S2 用 `continue-on-error: true` 允许失败**，S3 删除该行转为硬门禁；同时按 8.5 节只在 `push` 时运行，
   PR 上不跑 Testcontainers。
6. **已完成上下文的覆盖率门禁先行收紧**：在 `co-identity-domain/pom.xml` 覆盖
   `domain.coverage.minimum=0.70`（实测行覆盖 86%，留有余量），根 POM 保持 0 直到 S3 统一改为 0.70。
   这样“覆盖率门禁”在 S0 就是真门禁，而不是只跑一次报告——只跑报告不设阈值，等于把红线的判断权交回给人。
7. **红线**：渐进门禁只允许“缩小运行范围”。禁止 `-Dmaven.test.failure.ignore=true`、`@Disabled`、删除测试或修改断言；
   本文件每次修改都必须经 PR 评审。

配套的 Actions 用量优化（指导书 8.5 节）一并落地：

- `concurrency: { group: ci-${{ github.ref }}, cancel-in-progress: true }`：同分支新提交取消旧运行，避免排队重复计时；
- 集成测试 `if: github.event_name == 'push'`：PR 只做编译、单测、ArchUnit、覆盖率；
- `images` job 条件收紧为 `github.event_name == 'push' && github.ref == 'refs/heads/main'`：镜像只在发布路径构建；
- 保留 `actions/setup-java` 的 `cache: maven`；团队约定文档类改动在提交信息中加 `[skip ci]`，推送前先本地跑对应模块测试。

## 后果
- 正面：`develop` 从第一天起可以维持绿色，分支保护的“必须通过状态检查”得以真正开启；失败信号只剩“本 Sprint 真正该绿的测试”，
  定位成本低；用量集中在有价值的运行上（PR 轻量、push 全量）。
- 负面：**Sprint 范围之外的模块在 S3 之前没有回归保护**，若有人改动共享内核的语义，可能到 S3 才暴露——缓解手段是
  共享内核变更必须本地全量自检并在 PR 描述中说明影响面。
- 负面：允许失败的集成测试会以“黄色警告”形态长期存在，容易被当作噪声忽略；因此每次 Sprint 评审要记录其失败原因与数量趋势，
  防止“允许失败”悄悄变成“从不修复”。
- 负面：根 POM 的阈值仍为 0，尚未实现的上下文（Q&A / Reputation / Discovery 的 domain 模块）暂不设门槛；
  若 S1、S2 忘记按模块提阈值，覆盖率门禁对它们仍是空转，需要在 Sprint 计划会上一并确认。
- 后续行动：① S1 给 `co-qa-domain`、S2 给 `co-reputation-domain` 各自覆盖 `domain.coverage.minimum=0.70`
  （Identity 已在 S0 收紧）；② 提交 `frontend/package-lock.json` 后为 `setup-node` 启用 `cache: npm`；
  ③ S3 删除 `SPRINT_MODULES` 与 `continue-on-error`、根 POM 改 0.70，并回写本 ADR 的状态。

## 被否决的替代方案
- **保持全量门禁**：`develop` 长期红灯，分支保护无法开启；为了合并只能关检查，等于放弃 CI。
- **用 `-Dmaven.test.failure.ignore=true` 让测试“不阻塞”**：所有真实回归一起被静默，且违反“不改测试求变绿”的红线。
  相比之下，按模块缩小范围仍保留了“跑到的必须真绿”这一约束。
- **等实现全做完再打开 CI**：Sprint 0 的出口条件就是“CI 与 Backlog 就绪”，且失去早期反馈；集成问题会堆积到 S4 集中爆发。
- **用 `paths-ignore`（如 `docs/**`）跳过 job**：被跳过的 job 不会上报状态，分支保护里的必需检查将永远 pending，反而阻塞合并；
  文档类提交改用 `[skip ci]` 约定达成同样目的且不破坏必需检查。
- **给 frontend 加 Playwright E2E**：演示脚本人工走查性价比更高，且 E2E 在共享额度下是分钟数黑洞。
